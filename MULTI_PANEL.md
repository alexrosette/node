# Multi-panel: одна нода на несколько панелей

Этот форк Remnawave Node позволяет подключить **один контейнер ноды сразу к нескольким панелям Remnawave** (до 32). У каждой панели свои пользователи, при этом все они работают на одном Xray Core.

## Быстрый старт

1. В каждой панели создайте ноду с адресом вашего сервера. Порт можно указать **один и тот же во всех панелях** (например 2222) или разный, см. «Порты» ниже.
2. Из каждой панели скопируйте `SECRET_KEY`.
3. Пропишите всё в `docker-compose.yml`:

```yaml
services:
  remnanode:
    image: ghcr.io/alexrosette/node:latest
    container_name: remnanode
    hostname: remnanode
    network_mode: host
    restart: always
    cap_add:
      - NET_ADMIN
    ulimits:
      nofile:
        soft: 1048576
        hard: 1048576
    environment:
      # Все панели на одном порту 2222
      - NODE_PORT=2222
      - SECRET_KEY=... # панель #1
      - SECRET_KEY_2=... # панель #2
      - SECRET_KEY_3=... # панель #3
```

### Порты

- **Один порт на все панели (по умолчанию).** Если у панели N не задан `NODE_PORT_N`, она работает на общем `NODE_PORT`. Нода различает панели по **SNI**: каждая панель Remnawave при подключении отправляет свой уникальный SNI, вычисленный из её CA и JWT-ключа. Панели 3.3.0–3.4.4 шлют его всегда, в 3.4.5+ за это отвечает `SERVICE_SNI_VERIFICATION` в `.env` панели, по умолчанию `true`. **Не выключайте её**: без SNI панель на общем порту не подключится.
- **Отдельный порт.** Если задать `NODE_PORT_N`, панель N работает на своём порту, как раньше. SNI ей не нужен.
- Режимы можно смешивать: например, панели 1 и 2 на общем порту, а панель 3 на своём.

Образ собирается GitHub Actions ([.github/workflows/fork-ghcr.yml](.github/workflows/fork-ghcr.yml)) для amd64 и arm64:

| Тег | Когда обновляется |
|---|---|
| `ghcr.io/alexrosette/node:latest` | каждый push в `main` |
| `ghcr.io/alexrosette/node:sha-<commit>` | конкретный коммит, для отката |
| `ghcr.io/alexrosette/node:1.2.3` | git-тег `v1.2.3` |

Обновление на сервере: `docker compose pull && docker compose up -d`.

Если задан только `SECRET_KEY`, нода работает как обычная upstream-нода. Пропуски в номерах допустимы, например только `SECRET_KEY_3`.

При старте нода проверяет каждый ключ и выводит список панелей:

```
│                 Multi-panel mode: 3 panels                 │
│          panel #1 → port 2222 (shared, SNI)                │
│          panel #2 → port 2222 (shared, SNI)                │
│          panel #3 → port 2222 (shared, SNI)                │
```

## Обязательные условия

- **Одинаковый конфиг-профиль на всех панелях:** те же inbound, теги, порты и Reality-ключи. Пользователи при этом разные.
- **Одинаковые плагины** (torrent-blocker, фильтры и т.д.) на всех панелях.

Если конфиги разойдутся, нода применит конфиг той панели, которая последней перезапустила ядро, и напишет warning в лог.

## Как это работает

### Изоляция панелей

Панель определяется на уровне TLS: по её SNI на общем порту или по порту, если он у неё отдельный. Дальше у каждой панели своё mTLS (CA и сертификат ноды из её `SECRET_KEY`) и **свой JWT-ключ**:

- неизвестный SNI на общем порту отклоняется ещё в TLS-рукопожатии;
- клиентский сертификат проверяется CA **той панели**, чей SNI или порт использован, поэтому сертификат панели 2 не пройдёт как панель 1;
- JWT проверяется ключом этой же панели.

Подделать панель через заголовки или тело запроса нельзя.

### Пользователи

Все панели идентифицируют юзеров по числовому ID, и у разных панелей эти ID пересекаются. Поэтому внутри Xray пользователи вторичных панелей получают префикс:

| Панель | ID в панели | `email` в Xray                        |
| ------ | ----------- | ------------------------------------- |
| #1     | `123`       | `123` (без изменений, как в upstream) |
| #2     | `123`       | `p2.123`                              |
| #3     | `123`       | `p3.123`                              |

Панели этого не видят: во всех ответах (статистика, IP-листы, отчёты torrent-blocker) нода убирает префикс и отдаёт каждой панели только её пользователей.

### Конфиг Xray

Нода хранит пользователей каждой панели отдельно. Конфиг для Xray собирается так: **базовый конфиг + пользователи всех подключённых панелей**.

- **Первая панель** запускает ядро как обычно.
- **Следующие панели** не перезапускают Xray: их пользователи добавляются через Xray API (hot sync). Соединения пользователей других панелей не рвутся.
- Повторный `start` с теми же пользователями ничего не делает: хеши сравниваются отдельно для каждой панели.
- `add-user`, `remove-user` и т.д. от панели затрагивают только её пользователей.
- Если s6 сам перезапустит упавший Xray, тот получит актуальный конфиг со всеми пользователями, включая добавленных через API.

Полный рестарт ядра (обрывает соединения всех панелей) происходит только если:

- ядро не запущено;
- панель прислала `forceRestart` (кнопка перезапуска ноды в панели);
- изменился базовый конфиг (профиль);
- нужно применить больше 1 000 000 изменений пользователей разом (`HOT_SYNC_MAX_OPERATIONS`);
- изменения на входах Shadowsocks-2022 заняли бы больше ~10 с (`HOT_SYNC_MAX_SHADOWSOCKS_COST`). Xray перестраивает список юзеров такого входа на каждое изменение, поэтому 5 тыс. юзеров идут ~9 с, а 20 тыс. — ~130 с, и рестарт дешевле.

Скорость hot sync для VLESS и Trojan — около 8 500 изменений в секунду (400 тыс. юзеров ≈ 48 с). Пока он идёт, запросы `start`, `add/remove-user` и `stop` от других панелей ждут, а статистика и `get-system-stats` отвечают сразу.

### Остановка

Если панель останавливает ноду (отключили ноду в панели), **отключаются только её пользователи**, а Xray продолжает работать для остальных. Ядро останавливается полностью, только когда его остановила последняя панель.

### Статистика

Счётчики трафика в Xray общие: кто прочитал их с `reset`, тот «забрал» трафик у остальных. Поэтому нода сама вычитывает счётчики и раскладывает их по буферам панелей:

- **трафик пользователей** уходит только той панели, которой принадлежит пользователь;
- **трафик ноды** (inbound и outbound, из него панель считает «использованный трафик» ноды, историю и лимит) **делится между панелями пропорционально трафику их юзеров** за тот же интервал, uplink и downlink отдельно. Если юзеры панели 1 скачали 6 ГБ, а панели 2 — 3 ГБ, то панель 1 запишет на ноду 6 ГБ, панель 2 — 3 ГБ. Сумма по всем панелям равна реальному трафику сервера. Трафик без владельца (служебный API Xray) делится поровну;
- каждая панель читает и обнуляет **только свой буфер**.

Системные метрики (CPU, RAM, uptime Xray) общие и одинаковые для всех панелей.

### Плагины

- Отчёты torrent-blocker уходят панели, чей пользователь попался.
- Если одна панель прислала пустой набор плагинов, а другие ещё используют плагин, он не сбрасывается.
- Списки игнорируемых пользователей torrent-blocker сравниваются по ID без префикса.

## Управление из ledger

Ledger — отдельный «пульт» ноды. Он задаёт базовый конфиг Xray, перезапускает, останавливает и запускает ядро и смотрит состояние. Панели при этом только раздают своих юзеров. Полный контракт описан в `vpn-ledger/docs/node-control.md`.

Как включить:

```yaml
    environment:
      LEDGER_SECRET_KEY: "<из nodectl_keygen>"   # тот же формат, что SECRET_KEY
      LEDGER_STATE_DIR: "/var/lib/remnanode"     # по умолчанию тоже /var/lib/remnanode
    volumes:
      - "/var/lib/remnanode:/var/lib/remnanode"
```

Ledger подключается к `NODE_PORT`, его TLS-контекст выбирается по SNI. Поэтому с ledger этот порт всегда работает как общий, даже если панель одна. Ledger не панель: его нет среди панелей, у него нет юзеров и своей статистики.

**Пока ledger не прислал конфиг** (`base.source: panel`), нода работает как раньше: базовый конфиг берётся из панелей.

**После `PUT /node/ledger/config`** (`base.source: ledger`) правила такие:

- `start` от панели приносит только её юзеров. Базовый конфиг панели и `forceRestart` игнорируются, юзеры применяются hot sync без рестарта. Рестарт возможен только если hot sync невозможен или ядро не запущено.
- `stop` от панели снимает только её юзеров. Ядро продолжает работать, даже если панель была последней.
- Если ядро остановил ledger (`core/stop`), панели не могут его запустить. Запускает только ledger (`core/start`, `core/restart` или новый конфиг).
- База сохраняется в `LEDGER_STATE_DIR/base-config.json` (каталог 0700, файл 0600, запись атомарная). При старте контейнера ядро сразу поднимается с этой базой, а юзеров потом приносят `start` панелей.
- Перезапуск или новый конфиг — не чаще раза в 10 с, иначе 429. Конфиг, который не прошёл `xray -test`, возвращает 422 с выводом Xray, ядро при этом не трогается. Несовпавший `baseHash` возвращает 409.
- Хеш базы — `sha256` канонического JSON. Он совпадает с `config_hash()` в ledger: `json.dumps(sort_keys=True, ensure_ascii=False)`.

Ручки (только для ledger, панелям отвечают 404):

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/node/ledger/status` | ядро, база, панели (юзеры, последний start и запрос), система |
| GET | `/node/ledger/config` | текущая база и её хеш; 404, если базы от ledger ещё нет |
| PUT | `/node/ledger/config` | `{config, baseHash?}`: проверка, сохранение, рестарт |
| POST | `/node/ledger/core/restart` | `{reason?}`: рестарт с хуками плагинов |
| POST | `/node/ledger/core/stop` | остановить ядро для всех панелей |
| POST | `/node/ledger/core/start` | запустить ядро |

Авторизация: mTLS по CA из `LEDGER_SECRET_KEY` + `Bearer` JWT RS256 с `aud = rw-node-ledger`, `exp - iat ≤ 60 с` и уникальным `jti` (повтор в течение 120 с отклоняется). При отказе нода отвечает 401 и закрывает сокет. Каждый вызов пишется в лог ноды.

Откат: убрать `LEDGER_SECRET_KEY`, удалить `base-config.json` и пересоздать контейнер.

### Рестарт без «нода не на связи» в панелях

Remnawave считает ноду упавшей, если `get-system-stats` не ответил или вернул `xrayInfo: null`. Две такие проверки подряд — и панель шлёт `start`. Поэтому нода держит в памяти последний удачный ответ Xray и отдаёт его со свежими CPU, RAM и сетью в двух случаях:

- пока идёт рестарт, который начала сама нода (не дольше 60 с);
- если с последнего удачного ответа прошло не больше 30 с.

Если ядро остановили намеренно, кеш не отдаётся. Если ядро не поднялось за 60 с, панели видят правду.

Перед каждой остановкой ядра нода забирает счётчики трафика в буферы панелей, поэтому трафик при рестарте не теряется. `start` панели, который ждал окончания рестарта, повторно ядро не перезапускает, даже с `forceRestart`. Это работает и без ledger.

## Ограничения

- `forceRestart` или смена профиля в любой панели перезапускает ядро для всех.
- `drop-ips` и nftables-блокировки (block/unblock IP) действуют на всю ноду.
- Если поменять, какая панель числится как `#1`, у пользователей изменятся префиксы. После рестарта ядра всё синхронизируется само.
- Разбивка трафика ноды **по отдельным тегам** inbound/outbound приблизительная: Xray не сообщает, через какой тег шёл конкретный юзер. Итоговый трафик ноды по каждой панели точный.

## Тесты

End-to-end тест с настоящим Xray Core: три фейковые панели со своими CA и JWT, реальный трафик через VLESS-клиента, проверка изоляции, hot sync, статистики, stop и регрессии в режиме одной панели. Сценарий `ledger.mjs` проверяет управление из ledger: авторизацию, разделение ручек, базу от ledger, рестарт под опросом панелей и подъём с сохранённой базой.

```bash
npm ci
make image PLATFORM=linux/arm64 TAG=multipanel   # или linux/amd64
IMAGE=rwnode:multipanel ./e2e/multi-panel/run.sh
```

## Обновление на новые версии upstream

Изменения сосредоточены в нескольких местах:

- `src/common/multi-panel/` — панели из env, ID панели в запросе, префиксы пользователей;
- `src/main.ts` — отдельный HTTPS-листенер на каждую панель;
- `src/common/guards/jwt-guards/strategies/validate-token.ts` — JWT-ключ по панели;
- `src/modules/internal/internal.service.ts` — состояние по панелям и сборка общего конфига;
- `src/modules/xray-core/xray.service.ts` — start с hot sync, stop по панели;
- `src/modules/handler/handler.service.ts` — операции с пользователями с учётом панели;
- `src/modules/stats/stats-ledger.service.ts` — буферы статистики по панелям;
- `src/modules/_plugin/**` — плагины и отчёты torrent-blocker по панелям;
- `src/common/multi-panel/ledger.ts`, `src/modules/ledger/` — управление из ledger;
- `src/common/utils/core-restart.ts` — флаг рестарта ядра (кеш `get-system-stats`).

Чтобы обновиться: `git fetch upstream --tags && git merge <новый тег>`, затем прогнать e2e-тест.
